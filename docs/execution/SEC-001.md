## Deployment incident and permanent correction

The initial rotation run exposed a flaw in the temporary fallback design:
`docker rename` changed the container name but did not remove its Docker Compose
labels. `compose up db` therefore recreated and deleted the renamed fallback.
The error handler then removed the new SQL container before discovering that
the fallback no longer existed. No volume was deleted (`docker rm` never used
`-v`), both database backup pairs were verified, and no database restore or
secret rollback was performed.

The permanent correction removes rename/delete fallback behavior. If the SQL
container is missing, deployment parses (never sources) `deploy-state.env` from
the last successful release, requires an immutable `sha256` image plus a valid
named volume, verifies both exist locally, and sets `DB_RUNTIME_PINNED=true`
before Compose can run. Unexpected Compose `db` containers fail closed. The
recovered container's image, volume and loopback binding are checked before
backup, migration and application rollout.

## Rollback and recovery

- Never restore an old or compromised DB/JWT/encryption secret. Recovery is
  roll-forward with the current production environment.
- Before database mutation, create and verify one timestamp-matched backup for
  each of `GTAS_VPP_LIVE` and `GTAS_MENU`.
- If schema/data recovery is required, keep writers stopped and use
  `deploy/restore-db-pair.sh`; restore both databases as a pair and then start
  applications only after health checks pass.
- The account containment backup permits a deliberate data restore, but doing
  so would reactivate compromised demo identities and is therefore not the
  normal rollback. Provision trusted accounts in LEAN-02 instead.
