## Objective

Provide a repeatable SQL Server integration and browser-test boundary that cannot
silently use a shared or production database:

1. create a unique disposable SQL Server database boundary for every run;
2. apply the real EF migrations and required reference SQL/stored procedures;
3. seed deterministic employee, manager, procurement and system-admin personas plus
   own/department/company request data;
4. prove reset, rerun, concurrency, crash recovery and guarded cleanup;
5. allow authenticated or mutating Playwright tests only after explicit opt-in,
   loopback URL checks and a backend-confirmed database identity.

## Why now

The previous UI harness could reuse a configured/local server and the current tests
include permission and order mutations. In-memory tests cannot exercise SQL Server
stored procedures, cross-database references, migrations or real transaction behavior.
QA-001 is therefore a CP0 safety dependency before authorization and business-rule work.

## Implemented scope

### SQL/database fixture

- Added `gtas_vpp_test_support`, shared by backend integration and UI tests.
- A run ID is exactly 12 uppercase hexadecimal characters.
- Its only accepted server/database pair is
  `(localdb)\GTASVPP_QA_<run>` / `GTAS_VPP_TEST_QA_<run>`.
- Main and fixed-name companion `GTAS_MENU` database files are created under the run's
  `%TEMP%` directory, avoiding collision with an existing user database file.
- `dbo.__GTASQARun` records purpose `GTAS_VPP_QA_TEST`, run ID, database name and
  fixture version `qa-001-v1`.
- Cleanup first enumerates the isolated instance's user databases. It refuses an
  unexpected database, orphan `GTAS_MENU`, missing marker or mismatched identity.
- Runtime account password, JWT key and encryption key are random and kept in memory.
  The crash manifest contains only non-secret identity and process-owner metadata.
- The UI harness recovers manifests owned by dead processes before starting a new run,
  while skipping any fixture whose owner process is still alive.

### Backend identity handshake

- Added a strict `QaFixtureIdentityContract` in the backend service layer.
- `QaFixture:Enabled` is accepted only for host environment `Testing`, `TestEnv`, the
  exact run-specific LocalDB pair and integrated security without SQL credentials or
  `AttachDbFilename`.
- The hidden anonymous endpoint `/internal/qa/database-identity` exists only when that
  contract resolves. It re-queries the marker and returns 503 on mismatch.
- Normal Aspire development behavior is preserved: the QA environment and endpoint are
  enabled only when the explicit `qa-fixture-run-id` parameter is supplied by the test
  harness.

### UI harness

- `IAuthenticatedUiTest` requires `GTAS_E2E_ISOLATED=1` and always owns a fresh fixture.
- `IMutatingUiTest` additionally requires the exact acknowledgement
  `GTAS_E2E_MUTATION_OPT_IN=I_UNDERSTAND_THIS_MUTATES_QA_DATA`.
- All existing authenticated classes were marked; order creation and permission toggle
  were marked mutating. Anonymous compose/accessibility tests remain non-mutating.
- Before browser launch, both Aspire endpoints must be HTTP(S) loopback and the backend identity
  response must exactly match purpose, run ID, version, environment and database name.
- External, non-HTTP(S) or non-loopback `UITEST_BASE_URL` is rejected; authenticated tests never reuse it.
- Aspire/application disposal happens before fixture cleanup even after test failure.

## Risks and rollback

| Risk | Impact | Mitigation/rollback |
|---|---|---|
| LocalDB is Windows-only | No cross-platform full-SQL claim | Keep Linux safety contracts; later add equivalent marker-aware container adapter |
| Existing SQL hard-codes `GTAS_MENU` | Cross-run collision if one instance is reused | Unique instance and physical file directory for every run |
| Test identity endpoint could leak into normal host | Test metadata exposure | Endpoint exists only under strict Testing/TestEnv/run-specific LocalDB contract |
| Cleanup uncertainty | Orphaned test resources rather than unsafe deletion | Refuse cleanup on marker/database mismatch; inspect/recover manually |
| Browser test fails mid-run | Orphan state | nested disposal, manifest recovery and verified post-failure cleanup |
| Reverting harness | UI tests lose safe mutation path | Revert this isolated task commit; no persistent DB rollback is needed |

No business migration or external data rollback exists. Source rollback is the task
commit revert. Test databases are disposable; if a guard refuses cleanup, retain the
instance for forensic inspection rather than weakening the guard or dropping blindly.
