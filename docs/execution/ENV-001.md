## Objective

Make database ownership a deployment concern, never a client or request concern:

- one immutable `TestEnv` or `LiveEnv` binding is selected by server configuration;
- authentication, authorization, reports, notifications, health checks, bootstrap,
  repositories, stored procedures and business services use that same binding;
- login payloads, browser state, cookies and JWTs cannot select a database;
- startup fails before opening a connection when binding/configuration is missing or
  contradictory;
- local/Aspire/production examples each express one explicit binding without a
  committed personal connection string.

## Audit findings

### P0 cross-database authorization path

The pre-task design allowed one logical request to cross database boundaries:

1. Login accepted a client-provided `Server` value.
2. The login stored procedure nevertheless ran through a scoped UnitOfWork that had
   already selected the default/current-claim database.
3. The backend then copied the client selection into a JWT `Server` claim.
4. Permission/report/notification paths used the startup-default `VPPContext`, while
   repositories, stored procedures and business services could resolve the claim and
   open the other named connection.

If both named connections existed, a credential and permission from one database
could therefore authorize operations against the other database. Realtime user/group
channels also lacked an environment boundary.

### Additional configuration risks

- Startup and request-time environment resolvers had different implicit fallbacks.
- A Development-only heuristic could silently remap logical Test to a physical Live-
  named database after loading `.env` with higher priority than normal deployment
  configuration.
- Bootstrap targets were parsed independently from the runtime binding.
- Aspire supplied a logical environment but no explicit connection and could fall
  back to a committed developer-machine connection.
- Test and Live used a generic JWT audience; accidental signing-key reuse would make
  tokens transferable across deployments.
- The authenticated UI harness can attach to an arbitrary ready URL and includes
  permission mutation, so it is not safe for this task.

## Approved implementation contract

1. Keep `DatabaseSettings:DefaultEnvironment` for deployment compatibility, but make
   it required and normalize only the two canonical values `TestEnv` or `LiveEnv`.
2. Resolve one immutable `DatabaseBinding` before registering runtime contexts.
3. Require the selected named connection, validate its syntax and database identity,
   and reject any non-empty opposite Test/Live connection.
4. `DatabaseInitialization:Environments` must contain exactly the bound environment;
   bootstrap cannot target a second database.
5. Direct DbContexts, dynamic context factory, UnitOfWork, health and bootstrap receive
   the same binding; public APIs have no environment argument or reinitialization path.
6. Legacy `Server` claims and unknown login JSON fields are ignored. New DTOs, JWTs,
   cookies and frontend state contain no environment selection.
7. JWT audience is explicit and environment-specific; rollout deliberately requires
   one re-login and Test/Live deployments must retain separate signing keys.
8. Local Compose uses physical database `GTAS_VPP_TEST`; production remains
   `GTAS_VPP_LIVE`. Aspire/direct development require an explicit secret connection.
9. No environment badge is shown: the environment is operational metadata and adds
   no value to the normal user journey.
10. `GTAS_MENU` remains the app-owned companion catalog required by the existing SQL
    views/procedures. One binding therefore means one isolated SQL environment/instance
    containing the main catalog plus its companion; Test and Live must never share the
    same SQL instance or volume.
